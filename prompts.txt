Dialogue-to-Exact-Video-Frame Finder — AI/LLM Prompts
======================================================

Per the Quest1 Submission Process Flowchart, this file records every prompt
that materially influences the solution, including relevant iterations.

------------------------------------------------------------------------
1. Semantic fallback candidate selection (src/dialogue_frame_finder/semantic.py)
------------------------------------------------------------------------

Role in the pipeline: OPTIONAL, non-authoritative on timing. This prompt is
only sent when lexical/fuzzy indexed retrieval (the primary path) found
either no confident match at all, or a genuinely ambiguous one (two
candidates scoring nearly identically). Per design.docx section 15, the
LLM's role is limited to semantic transcript matching among ALREADY-LOCATED
candidate windows -- it is never asked for, and never permitted to invent,
a timestamp, frame number, or word it wasn't given. Its response only
selects which candidate (by an id the code generated, not the model) is
the best match; the actual onset timestamp is still derived afterward from
that candidate's own word-level ASR alignment via the same verify_window
path used everywhere else. If the model names a candidate_id that was never
offered to it, the code rejects the answer outright (see
parse_semantic_response) rather than trusting it.

Model used: claude-sonnet-5 (Anthropic API), temperature=0 for determinism.

Exact prompt template (see build_semantic_prompt in semantic.py --
{target_text} and {candidate_list} are filled in at call time; the
candidate list format is "- id=<id> start=<seconds>s text=\"<transcript
text for that window>\""):

    Given a target dialogue and timestamped transcript candidates, select
    the candidate that most likely represents the target. Do not invent
    words or timestamps. Return structured JSON containing candidate_id,
    match_confidence, and rationale. If the evidence is insufficient,
    return NO_CONFIDENT_MATCH.

    Target dialogue: "{target_text}"

    Candidates:
    {candidate_list}

    Respond with ONLY a JSON object, no other text, in exactly this shape:
    {"candidate_id": "<id or null>", "match_confidence": <0.0-1.0>, "rationale": "<short reason>"}
    Use candidate_id null and match_confidence 0.0 if none of the
    candidates plausibly represent the target (NO_CONFIDENT_MATCH).

Iterations / design notes:
- This is the exact constrained-matching template from design.docx section
  15's worked example ("select the candidate that most likely represents
  the target... Do not invent words or timestamps... Return structured
  JSON containing candidate_id, match_confidence, and rationale... If the
  evidence is insufficient, return NO_CONFIDENT_MATCH"), adapted only to
  fill in the concrete candidate-list format the code actually produces.
- candidate_id is deliberately an opaque code-generated string (c0, c1,
  ...), not a timestamp or transcript excerpt, so the model has nothing
  timestamp-shaped to hallucinate a variant of.
- match_confidence returned by the model is used as this candidate's
  reported confidence score in the final output -- appropriate specifically
  because this path only runs when the lexical score was already
  established as insufficient by construction (no-match or ambiguous).

2. Development assistance (Claude Code / Sonnet 5)
------------------------------------------------------------------------

Claude Code (Sonnet 5) was used as the coding assistant that designed and
implemented this entire solution, under interactive direction and review at
every phase. This is developer assistance, not a component of the running
pipeline (see design.docx section 15 / requirements.docx section 6, which
concern LLM usage *inside* the solution itself -- item 1 above) -- but the
prompts below materially shaped the architecture and are recorded here for
full transparency into how the solution was built, per the user's explicit
request. Listed chronologically; paraphrased where a prompt was very long,
quoted closely where it set a specific architectural constraint. Routine
"looks good, continue" acknowledgments are omitted; substantive direction is
kept in full.

2.1 Initial analysis (no code)
  "I have three project specification documents in this folder:
  @requirements.docx @design.docx @test-plan.docx. Read all three documents
  carefully. For this step ONLY, do not write code... [12 analysis
  questions: problem definition, I/O contract, architecture, dialogue
  localization, frame determination, ASR-error/multi-candidate handling,
  ambiguity handling, YouTube generalization, test requirements, repo
  structure, risks/assumptions, ambiguities in the specs]... interpret the
  target dialogue as SPOKEN dialogue in the video's audio track. Do not
  assume ... visually displayed as text/subtitles... give me a phased
  implementation plan for building the project."

2.2 Architecture revision: indexed retrieval (no code)
  "Before you proceed to Phase 0 or write any code, I want to revise and
  clarify the dialogue-search algorithm based on further reasoning I have
  done... I do NOT want a brute-force sliding-window search over the entire
  transcript to be the primary retrieval mechanism." Specified, in detail:
  build an in-memory inverted transcript index (word -> occurrences with
  position/start/end); rank target words/phrases as search anchors by
  transcript-local rarity ("should NOT depend on one distinctive word
  always existing"); retrieve candidates from the index, then verify each
  by comparing the ENTIRE target phrase against a local neighborhood
  (tolerant of ASR insertions/deletions/substitutions); use fuzzy retrieval
  only as a fallback when indexed retrieval fails; "Find ALL sufficiently
  strong valid occurrences, not just the highest-scoring... Do NOT simply
  choose the highest similarity score" -- the earliest valid occurrence in
  video time must be returned; onset must come from the first target
  word's own timestamp, refined locally by audio analysis; frame mapping
  must use decoder PTS, never timestamp*FPS. Requested: agreement/critique
  of this approach vs. sliding-window, weaknesses + fallbacks, index
  representation, neighborhood selection, multi-occurrence handling, ASR-
  error handling, onset->frame mapping, then a revised 9-phase plan
  (feasibility / index+retrieval / verification / audio alignment / frame
  extraction / full pipeline / testing / real E2E / calibration+docs) and
  synthetic test cases for 8 named scenarios. "Do not start implementation
  until I explicitly tell you to proceed."

2.3 Onset-refinement correction (no code)
  "Do not assume VAD is the primary mechanism for determining the exact
  dialogue onset. The actual requirement is the onset of the FIRST TARGET
  WORD, not the beginning of general speech... word-level ASR/alignment for
  the first target word is the primary timing signal; local audio/VAD/
  energy analysis may refine or validate that estimate; VAD must never move
  the result to an earlier unrelated speech region simply because speech
  was already occurring." Also requested: an evaluation of whether a
  separate forced-alignment model is needed vs. faster-whisper timestamps +
  local refinement, and two specific synthetic test cases -- target
  following other speech with no pause ("Well, I think MY MIND rebels at
  stagnation"), and target starting while another speaker is already
  talking.
